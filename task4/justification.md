# Обоснование конфигурации Terraform (Yandex Cloud)

## Выбор облака и способа развёртывания

- **Yandex Cloud, регион `ru-central1` (РФ).** Медицинские и финансовые данные «Будущего 2.0» подлежат хранению на территории РФ (152-ФЗ, требования ЦБ РФ) — российский провайдер закрывает требование резидентности из коробки.
- **Доступность для стенда.** Новый аккаунт со стартовым грантом покрывает стоимость учебного стенда; после `apply` и скриншота выполняется `terraform destroy`, поэтому расходы остаются в пределах гранта.
- **Установка провайдера из РФ.** Провайдер `yandex-cloud/yandex` ставится через официальное зеркало `https://mirror.yandex.ru/terraform-providers/` (настроено в `~/.terraformrc`), что исключает зависимость от внешних реестров.
- **Аутентификация через YC CLI.** Terraform берёт учётные данные из `~/.config/yandex-cloud/credentials` — токены не лежат в коде и состоянии.

## Почему декларативный подход и IaC

1. **Воспроизводимость.** `terraform apply` в пустом каталоге создаёт идентичный ландшафт. Окружения dev/test/prod и среды новых доменов (фарма, электроника) создаются сменой переменных `env`/`project`, а не вручную — исключаются дрейф конфигураций и «снежинки».
2. **Масштабируемость.** Размеры ВМ, дисков и CIDR вынесены в `variables.tf`: вертикальное масштабирование — правка переменной и `apply`; горизонтальное — тиражирование конфигурации на новые домены без переписывания кода.
3. **Управляемость и безопасность изменений.** `terraform plan` показывает дельту до применения; изменения инфраструктуры проходят код-ревью в пул-реквесте, как код приложений; при аварии ландшафт восстанавливается из кода за минуты.

## Выбор ресурсов и параметров

| Ресурс | Параметр | Обоснование |
|---|---|---|
| VPC + 4 подсети | `platform`, `clinics`, `fintech`, `ai` | Соответствует доменам из Заданий 1–2: сетевая изоляция мед- и финконтуров, независимое развитие доменов |
| NAT-шлюз (`shared_egress_gateway`) | `gateway_id` у всех подсетей | Приватные узлы (аналитика, шина, БД) получают исходящий доступ (обновления ОС, внешние API), но недоступны из интернета: ниже поверхность атаки для мед- и финданных; одна аудируемая точка выхода; дешевле и безопаснее публичных IP на каждом узле |
| Статический публичный IP | только у портала | Единственная публичная точка входа — портал самообслуживания «витрина данных» за SG с портами 80/443 |
| VM `portal` | 4 vCPU / 8 ГБ, data-диск 50 ГБ | Веб-приложение портала с конструктором отчётов: достаточно для dev-нагрузки; рост — вертикальным масштабированием через переменную `vm_sizes` |
| VM `analytics` | 8 vCPU / 16 ГБ + 200 ГБ network-ssd | Демо MPP-узла витрин: колоночные СУБД требовательны к CPU и памяти; отдельный быстрый SSD-диск данных под витрины и преагрегаты |
| VM `integration` | 4 vCPU / 8 ГБ | Узел шины данных (Kafka) для событийной интеграции доменов — замена легаси-ESB |
| Диски | boot 30 ГБ + отдельные data-диски `network-ssd` | Данные отделены от ОС: изменение размера и снапшоты без пересоздания ВМ; `network-ssd` — баланс цены и IOPS для dev-стенда |
| Object Storage bucket | `acl = private` | Озеро данных Bronze: дешёвое горизонтальное хранение сотен ТБ, S3-совместимый API для ETL и ИИ; приватный ACL — данные не доступны извне |
| Managed PostgreSQL | `s2.micro`, 20 ГБ, `PRESTABLE`, без публичного IP | БД домена «Клиники» как управляемый сервис: провайдер отвечает за бэкапы, патчи и отказоустойчивость; приватный хост в подсети `clinics` — медданные не выставляются наружу; в prod `PRESTABLE` заменяется на `PRODUCTION` и больший пресет |
| Security groups | минимальные привилегии | SSH только из корпоративного CIDR; сервисные порты (5432–9092) только внутри VPC; наружу — только 80/443 портала |

## Что разворачивается вручную и почему

- **Сервисный аккаунт `terraform-sa` и статические ключи** — создаются командой `yc iam ...` вручную (разделение обязанностей): Terraform получает только готовые учётные данные через `terraform.tfvars`, роль `editor` выдаётся точечно под каталог.
- **Секреты (пароль БД, SSH-ключ, ключи Object Storage)** — не лежат в коде и состоянии Terraform в открытом виде (помечены `sensitive`), в боевом режиме подаются из Vault/секрет-менеджера CI.
- **Деплой приложений (портал, Kafka, ClickHouse)** — Terraform отвечает только за инфраструктуру; приложения ставятся пайплайнами CI/CD поверх ВМ — разделение ответственности IaC и delivery.
- **TLS-сертификаты и DNS** — требуют внешних процедур (CA, регистратор) и подключаются к созданным Terraform ресурсам (статический IP портала).

## Управление стоимостью стенда

Минимальные пресеты для dev (`s2.micro`, 4/8 и 8/16 vCPU), `PRESTABLE` для БД, единый NAT вместо публичных IP и обязательный `terraform destroy` после проверки — суммарная стоимость стенда укладывается в стартовый грант аккаунта.

## Итог

Конфигурация автоматизирует весь инфраструктурный слой целевой архитектуры (сеть, NAT, безопасность, ВМ, диски, озеро данных, управляемая БД), оставляя вручную только security- и application-слой. IaC даёт воспроизводимость окружений доменов, скорость онбординга новых направлений и контролируемую масштабируемость — ключевые требования «Будущего 2.0».
