# Обоснование конфигурации Terraform (LocalStack)

## Почему LocalStack

LocalStack эмулирует AWS-сервисы (EC2, S3, RDS, VPC) локально в Docker: `terraform apply` создаёт реальную (эмулированную) инфраструктуру без облачного аккаунта и затрат. Конфигурация переносима: для боевого AWS достаточно убрать локальные endpoints и подставить настоящие учётные данные — код ресурсов не меняется.

## Почему декларативный подход и IaC

1. **Воспроизводимость.** `terraform apply` в пустом LocalStack/облаке создаёт идентичный ландшафт. Окружения dev/test/prod и среды новых доменов создаются сменой переменных (`env`, `project`), а не вручную — исключаются дрейф и «снежинки».
2. **Масштабируемость.** Размеры ВМ, дисков и CIDR вынесены в `variables.tf`: вертикальное масштабирование — правка переменной и `apply`; горизонтальное и тиражирование на новые домены (фарма, электроника) — модули и `for_each` без переписывания кода.
3. **Управляемость изменений.** `terraform plan` показывает дельту до применения; изменения проходят код-ревью в пул-реквесте; состояние и история — в Git; при аварии ландшафт восстанавливается из кода.

## Выбор ресурсов и параметров

| Ресурс | Параметр | Обоснование |
|---|---|---|
| VPC + подсети | public-platform, private-platform, clinics a/b, fintech, ai | Соответствует доменам из Заданий 1–2: сетевая изоляция мед- и финконтуров; две подсети клиник (две AZ) — задел под отказоустойчивость БД |
| Internet Gateway + NAT Gateway + EIP | приватные подсети маршрутизируются через NAT | Приватные узлы (аналитика, шина, БД) получают исходящий доступ (обновления, внешние API), но недоступны из интернета: ниже поверхность атаки для мед- и финданных, одна аудируемая точка выхода |
| Публичный EIP | только у портала | Единственная публичная точка входа — портал самообслуживания за SG с портами 80/443 |
| EC2 portal | c5.xlarge (4 vCPU / 8 ГБ) + data-диск 50 ГБ | Веб-портал с конструктором отчётов; compute-optimized под веб-нагрузку dev-стенда |
| EC2 analytics | c5.2xlarge (8 vCPU / 16 ГБ) + 200 ГБ gp2 | Демо MPP-узла витрин: колоночные СУБД требовательны к CPU/памяти; отдельный быстрый диск под данные |
| EC2 integration | c5.xlarge (4 vCPU / 8 ГБ) | Узел шины данных (Kafka) для событийной интеграции доменов |
| EBS data-диски | отдельно от boot (gp2) | Данные отделены от ОС: изменение размера и снапшоты без пересоздания ВМ |
| S3 bucket | private | Озеро данных Bronze: дешёвое горизонтальное хранение сотен ТБ, S3-API для ETL и ИИ |
| RDS PostgreSQL | db.t3.micro, 20 ГБ, publicly_accessible = false | БД домена «Клиники» как управляемый сервис в приватных подсетях; в prod — класс выше и multi-AZ |
| Security groups | минимальные привилегии | SSH только из корпоративного CIDR; сервисные порты только внутри VPC; наружу — только 80/443 портала |

## Что разворачивается вручную и почему

- **IAM-роли и секреты (Vault)** — security-чувствительные объекты создаются вручную командой ИБ (разделение обязанностей); пароли и ключи не лежат в коде и состоянии Terraform.
- **Деплой приложений (CI/CD)** — Terraform отвечает за инфраструктуру; приложения (портал, Kafka, ClickHouse) ставятся пайплайнами поверх ВМ.
- **TLS-сертификаты и DNS** — требуют внешних процедур (CA, регистратор), подключаются к созданным Terraform ресурсам (EIP портала).

## Итог

Конфигурация автоматизирует весь инфраструктурный слой целевой архитектуры (сеть, NAT, безопасность, ВМ, диски, озеро данных, управляемая БД), оставляя вручную только security- и application-слой. IaC даёт воспроизводимость окружений доменов, скорость онбординга новых направлений и контролируемую масштабируемость — ключевые требования «Будущего 2.0».
